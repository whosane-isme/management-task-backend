# ملاحظات مراجعة المتطلبات

## عيوب تم إصلاحها في التنفيذ

1. المخطط الأصلي نسي علاقات `activity_logs.task_id/user_id`؛ أضيفت كمفاتيح خارجية مع فهارس.
2. وضع `auth_provider` و`provider_id` داخل `users` يمنع الربط المرن بأكثر من مزود؛ فُصلا إلى `auth_identities` مع unique على `(provider, subject)`.
3. البريد واسم القسم كانا unique بحساسية حالة الأحرف؛ التنفيذ يستخدم functional unique indexes على `lower(...)`.
4. لم يكن المخطط يمنع `DEPARTMENT` من دون قسم؛ أضيف DB check constraint.
5. `action` كنص حر يجعل الـtimeline صعب التحليل؛ استبدل بـ`event_type` ثابت و`details` منظم.
6. لم يكن معروفًا من قام بالإسناد؛ أضيف `assigned_by_id`.
7. حذف الموظف كان سيكسر التاريخ؛ أضيف `is_active` وسيكون التعطيل هو المسار الطبيعي.

## قرارات أكدها صاحب المنتج

1. النظام لمؤسسة واحدة في V1، ولا نحتاج عزل multi-tenancy.
2. مدير المؤسسة يملك رؤية كل شيء، لكن شاشة التركيز الافتراضية لا تعرض كل شيء دفعة واحدة.
3. الأدوار والصلاحيات قابلة للتخصيص؛ يمكن لمساعد تنفيذي امتلاك صلاحيات تنظيم وعرض واسعة، ويمكن لمدير تقني أو HR أخذ صلاحيات عالية ضمن قسمه.
4. `PRIVATE` تظهر للمنشئ والمكلفين، ولمن يملك صلاحية إدارية صريحة تسمح برؤية الخاص.
5. الموظف يستطيع إنشاء مهام لنفسه، ولفريقه إذا امتلك صلاحية الإسناد المناسبة.
6. يمكن للموظف طلب مساعدة على مهمة، ويحدد نطاق الإعلان من visibility المهمة.

## قرار ما زال مفتوحًا

- هل إكمال بعض المهام يحتاج مراجعة/موافقة؟ لم نضف `IN_REVIEW` إلى V1.

## نواقص بيئة التطوير الحالية

- لا يوجد PostgreSQL أو Docker على الجهاز، لذلك تحققنا من migration عبر PostgreSQL SQL offline فقط، وليس upgrade/downgrade حقيقيًا.
- Git تهيأ محليًا على فرع `main`، لكن لا يوجد remote مربوط بعد.
- dependency lock كامل مؤجل إلى اختيار أداة إدارة الحزم/CI؛ `pyproject.toml` يقيد الإصدارات الرئيسية حاليًا.
